# ADR 001: Выбор стратегии управления состоянием и кэширования данных

## Статус
Принято (Accepted)

## Контекст
Приложению необходимо:
1. Кэшировать ответы API со `staleTime: 5000` (5 секунд) и поддержкой `stale-while-revalidate`.
2. Корректно прерывать HTTP-запросы через `AbortSignal` при размонтировании компонентов.
3. Поддерживать бесшовную точечную мутацию кэша при получении WebSocket-патчей без сетевого рефетча.
4. Синхронизировать UI-выделение между независимыми компонентами («Дерево» и «Таблица»).

## Решение
Разделить стейт на два изолированных контура:
1. **Серверное состояние:** Использовать **TanStack Query (React Query)**.
2. **Клиентское UI-состояние:** Использовать **React Context (`OrgUiContext`)**.

## Рассмотренные альтернативы

### Альтернатива 1: Redux Toolkit (RTK + RTK Query)
* **Минусы:** Избыточный бойлерплейт (actions, reducers, extraReducers), усложненная настройка для небольшого проекта.
* **Причина отказа:** TanStack Query предоставляет декларативное управление SWR-кэшем и отмену запросов без необходимости писать сотни строк шаблонного кода.

### Альтернатива 2: Zustand / Redux для всех состояний
* **Минусы:** Ручная реализация логики инвалидации по таймеру, отслеживания статусов `isLoading` / `isError` и работы с `AbortController`.
* **Причина отказа:** Переизобретение стандартных механизмов кэширования.

## Последствия
* **Положительные:**
  * Строгое соответствие нефункциональным требованиям ТЗ по кэшированию и отмене запросов.
  * Чистое разделение: UI не знает про HTTP-запросы, а работает с готовыми хуками.
* **Отрицательные:**
  * Необходимость вызывать `queryClient.setQueryData` вручную при сокетных патчах.
